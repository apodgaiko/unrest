# Disposable trusted-process cohort

The real opt-in route constructs per-role SQLite, log and temporary directories
and applies startup-sensitive controls on the owned backend argv before
`app-server`, as well as at thread creation. Ordinary managed authentication
and exact-thread-keyed persistence remain shared. No authentication store is
read or copied by the controller. Real effective configuration, auth/model
compatibility and continuation remain **UNVERIFIED** for genuine ACP reuse.
Genuine native approval and final-candidate timing are also **UNVERIFIED** under
the accepted release risk. Controlled local tests prove bounded local behavior
only. Experimental cohort dispatch and reuse are **disabled by default**.

The experimental module is separate from ordinary scheduling, task states and
`end_node`. It requires explicit trusted-process selection. Strong OS write
isolation, comprehensive unknown-descendant cleanup and transient
mutation/restoration detection remain unverified. Broker capabilities are
turn-bound; owned process handles are drained and reaped. This is for trusted
workloads in disposable directories, not an adversarial sandbox.

One `python -m unrest_harness.experimental_cohort run` invocation owns one async
event loop and one durable campaign journal across P1, P2, P3 and C1. It uses
the retained ACP implementation and actual provider-to-private-MCP completions;
controller-authored outcomes cannot complete turns. Original target identifiers
are included in each turn, and validator completions require an exact boolean
verdict map. Passing one target cannot hide dissent on another.

The existing executable model chooses priority, authored ties, reservations,
one reusable pair, correction and rotation. Fresh arms close transports between
turns. Only the first authored lane may retain the worker/validator pair. Final
validators each get fresh process/session identities and the integrated input
digest, with every original target. Early evidence cannot complete that gate.

## Custody and resources

Controller Git commands disable automatic maintenance and garbage collection
explicitly. Disposable candidates use bounded loose-object storage; background
maintenance is neither needed nor allowed to outlive the synchronous command.
System/global Git configuration and ambient environment are excluded.

Every lane has separate candidate Git storage, broker-editable files and owned
process storage. Path identities include device/inode and canonical ancestry;
links, unresolved paths, overlapping directories, shared caches and overlapping
writer/read footprints refuse admission. Local service identities collapse
loopback aliases and wildcard addresses to the same transport/port namespace.
External read inputs have retained bounded digests. Later observed input or
identity changes stop dispatch and integration; active turns drain under their
existing deadlines. Independent lanes may overlap validation and work.

The candidate observer's existing path, link, Git-object and size bounds remain
in force. This composition supports flat regular text inputs only, initially
at the declared clean base. It additionally caps files at 1 MiB and the complete
input context at 32 KiB. Unsupported trees fail instead of receiving broader
broker authority. Git metadata never enters a broker directory. Read-only extra
inputs accompany real turn instructions; only declared write files are broker
mutation capabilities.

After worker completion and broker revocation, the controller checks retained
inputs, stages only declared paths, checks staged scope, commits in disposable
Git, verifies resulting bytes and publishes a seal. A verified snapshot is
durably retained before its seal record. Validation checks inputs before and
after its turn; integration checks them again. Integration requires all model
lanes passing and copies only sealed bytes, serially in authored order, checking
the base, scope, staged paths and resulting tree at each step.
Snapshot copies preserve unexpected links for rejection without following them;
the complete copied snapshot must match the freshly observed manifest before
publication. Duplicate observations at the same seal transition do not delay
independent validation readiness.

`status --state PATH` reads a recovery projection without dispatch authority.
Loading running state invalidates sessions and treats outstanding reservations
as consumed uncertain sends. `recover --seal PATH --destination NEW_DIRECTORY`
copies only the last sealed snapshot. Dirty originals remain quarantined; this
does not reset correction history, resume sessions or create a new live budget.
Persisted status includes consumed final reservations, even when no final
completion arrives, plus the campaign total at that snapshot. Final reservation
accounting is checkpointed before send; it is not send proof. Read-only status
labels this as the last persisted snapshot; the durable journal remains the
record of reservations across a crash between checkpoints.

four episodes with one journal: 4+6+8+6=24 turns, including both fresh final
validators in each episode, 300 seconds per turn, 1800 seconds per episode and

Never reset the journal or restart a live campaign to recover missing results.

## Provider context and startup controls

The complete authentic `rust-v0.160.1` model catalogue is bundled unchanged,
SHA256 `fd219bd9f061278275f528939f82f54d2eb97df4b25c23b022adbe48813d920b`.
Its source is the pinned upstream
[models catalogue](https://raw.githubusercontent.com/openai/codex/rust-v0.160.1/codex-rs/models-manager/models.json).
It retains all metadata, including native-tool declarations. Native direct
writes remain within the unverified OS-isolation limit; their availability
alone does not refuse this trusted-process experiment. Intended mutations use
the private broker. Observed unauthorized changes quarantine the owner and
stop dispatch/integration without adopting the unexpected bytes.

Local config and instruction files, global AGENTS override/default selection
(including absence), rules, and host skill catalogues are privately sealed.
File bytes, directory membership, symlink targets and permission modes count.
The observer is bounded to 8192 entries, 1 MiB per file, 64 MiB total and a
five-second cooperative observation deadline. Read errors and unsupported
structures refuse. The controller neither inventories nor copies a whole home.
The common seal also binds the disposable runtime root and a no-local-context
rule: private role storage may not introduce `.agents`, `.codex`, `config.toml`
(including case aliases),
or symlink imports. A bounded names-only scan enforces this rule before sends
and at resource checks; normal SQLite, log and temporary files may change.
History, memories, context-management/token-budget imports, plugins, hooks,
apps, shell snapshots, bundled/cloud skills and each discovered host skill are
explicitly disabled with supported settings. Global instructions remain sealed
common inputs; project-doc suppression is not treated as global-doc suppression.

Every locally inherited MCP registration is explicitly disabled, including names
containing dots; an empty MCP table would recursively merge. The bridge reads
supported `config/read`, `configRequirements/read` and non-refreshing
`account/read` responses before releasing the backend initialization response.
It refuses mismatched settings, extra registrations, undeclared config layers,
unresolved managed requirements and account identity changes. It never retries
with wider permissions. Managed requirements and external selected profiles
that this route cannot resolve require attention, not bypass. Effective response
bodies are discarded; evidence contains only digests, counts and trust metadata.
This is a metadata guard, not proof of the complete native-tool inventory.

A single campaign ledger rejects repeated fresh session IDs across roles and
episodes; only a retained role can continue its own exact ID. Final gates
separately reject reused session IDs or process generations and retain dissent.
No latest-thread selection, cross-thread import/fork or identity fallback exists.
Reservations persist before send. Send observation follows an actual owned-pipe
write/drain; controlled backend receipt before acknowledgement is a separate
crash boundary. Ambiguous sends stay consumed. On halt, parked/unsent owners are
revoked promptly, sent unaffected turns retain their original deadlines, and
completed controller custody work is drained before cleanup. Successful sibling
completions remain recorded even though the cohort cannot integrate.

Drain permission is recorded synchronously before the coordinator stops a usable
shared ledger. An unrequested or already-expired ledger halt cannot gain that
permission retrospectively. If a synchronous owned journal operation initiates
the first halt before its failure callback, the ledger retains that operation
owner as causal provenance. The coordinator accepts only that retained owner
from its own cohort and still checks the original lifetimes and open ledger.
Otherwise a failing owner notifies the coordinator before halting the ledger,
allowing unaffected already-sent siblings to drain while
the failed owner remains quarantined and the cohort remains attention. Repeated
stop preserves permission already given; it neither clears failure nor permits
another send.

Successful retirement requires an actual non-uncertain journal acknowledgement
under the original ticket cutoff, followed by successful candidate verification,
sealing and completion persistence. A returned completion alone is insufficient:
the ledger can finish a ticket as uncertain without raising. Acknowledged custody
work retains the original episode/campaign lifetime; it does not receive a new
turn deadline or become late merely because custody crosses the acknowledgement
cutoff. The coordinator rechecks usable ledger/lifetime and owner state after
postprocessing, then starts retained owned cleanup before clearing sent-active
eligibility, without yielding. Thus a stopped drain has no live, unretired gap
for the watchdog. Actual cleanup and resource release barriers still complete
before capacity can be reused; cleanup uncertainty remains monotonic quarantine.

Candidate authority seals bind the declared write scope, original targets,
logical candidate/broker namespace, resource identities, permission modes and
common input digests to the candidate manifest. These observations precede and
follow validation and precede integration. Recovery copies the last published
Git seal only and grants no resumed execution authority.

The pinned adapter's read-only preset hardcodes `approvalPolicy=on-request`
on `turn/start`, overriding startup/thread defaults. The guarded bridge
therefore restricts that one field to `never`, retaining read-only sandboxing,
exact thread identity and every other turn field. Other frames are forwarded
unchanged. A wider or unknown turn policy refuses. Bounded protocol observations
record the explicit backend `thread/start` model/provider/effort and compare the
returned thread with the ACP identity; missing model/effort fields cannot pass
through the adapter's default-model fallback. This protocol restriction and
observation are additional controller controls, not OS confinement.

## Halt when persistence fails

The in-memory stop and parked/unsent broker revocation precede journal writes.
Stop-record, state-checkpoint and completion-consumption errors cannot bypass
sent unaffected turns: a retained, cancellation-shielded drain keeps their
original turn deadlines. Unsent tasks are cancelled and cannot acquire new
claims or send. No validation, integration or final phase is started after halt.
Cleanup attempts each failed operation a bounded number of times; it does not
retry until storage recovers. Owned teardown follows the drain, and secondary
errors are reported separately without replacing the initial stop/failure reason.

An authenticated private-MCP completion whose journal acknowledgement or custody
checkpoint fails is retained as `unconsumed_completions` when state remains
writable. It is not a sealed candidate or a passing coordinator result. The last
published candidate seal remains the recovery source. Failed acknowledgements
leave their reservations consumed and possibly uncertain; they never refund a
turn or reopen reuse. A failed checkpoint sets `persistence_failed` in returned
status. Disk recovery can only describe the last persisted snapshot, which may
omit later completions or stop records. Recovery always denies resumability;
unavailable persistence never turns a failed run into success.

## Controlled finite conformance

The finite priority checks establish all 25 ordered pairs of recheck,
correction, first validation, admitted work and unrelated admission. Independent
fresh controls establish each phase prefix through actual ACP sends, private
MCP completions and Git seals. Joining those completed test histories creates
a scheduling fixture, not a restart or resumed-session API. The next reservation
and send must select the independently expected priority and authored tie.

Completion-order tests use a separately pinned derivative of the controlled
backend. It records receipt and waits for an explicit release before starting
its HTTP completion exchange. The original backend and its two-second HTTP
timeout remain unchanged. A polling interval observes a release marker; elapsed
sleep is never the ordering oracle. All four worker/validator batch delivery
orders retain the production coordinator's authored consumption order.

The PP, RR, RP and RC scripts have respectively 6, 924, 28 and 210 causally
ordered two-lane completion words. Testing several boundary orders does not
alone exhaust those words. A reduction must establish that exchanging adjacent
independent-lane completions preserves each candidate, original targets,
correction history, generation and final authored integration. Its premises
include disjoint resources, sufficient reserved budget, bounded active and
parked occupancy, and separate exhaustive priority/batch checks. Stop, expiry,
resource drift and failure paths are outside that commutation argument and
require their own actual-process observations. Four-lane graph enumeration
remains simulation and proves no four-lane runtime occupancy.

TTL checks retain actual role processes and independently control the scheduler
clock at 3599, 3600 and 3601 seconds. The separate pilot lifetime remains real
and unexpired during these probes. This isolates the scheduling TTL guard; it
does not permit a real pilot episode to exceed its earlier 1800-second bound.

observed drift during an actual overlap stops new dispatch and integration.
